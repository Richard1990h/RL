1. PLATFORM OVERVIEW
================================================================================

Rally Live (rallylive.ca) is a live streaming, video sharing, and competitive
gaming platform. Think of it as a combination of Twitch (live streaming),
YouTube (video hosting), Snapchat (messaging), and a custom economy system
where credits flow between viewers, creators, and the platform.

Core pillars:
  - Live streaming with interactive game modes (battles, trivia, auctions)
  - Video hosting with upload, series, and recommendations
  - Real-time credit economy (donations, gifts, power-ups, services)
  - Social features (friends, messaging, notifications, follows)
  - Creator monetization (donations, ads, services marketplace)
  - FiveM/GTA RP server management websites
  - Progressive Web App with offline support

  - Owner accounts have additional device gating

5. BANKING & CREDIT SYSTEM (Core Financial Architecture)
================================================================================

FUNDAMENTAL RULE: 1 credit = $0.01 USD

All credits are stored as integers (no fractions). The system uses a
three-layer financial architecture:

Layer 1 - WALLET (Balance)
  Model: Wallet
  Fields: credits (current balance), totalEarned, totalSpent
  Rule: One wallet per user, auto-created on registration
  Read: GET /api/wallet returns balance + last 50 transactions

Layer 2 - TRANSACTIONS (History)
  Model: Transaction
  Purpose: User-facing transaction log
  Types: DEPOSIT, WITHDRAWAL, CREDIT_PURCHASE, CREDIT_SPENT,
         CREDIT_EARNED, DONATION, SUBSCRIPTION, AD_REVENUE,
         SERVICE_PAYMENT, SERVICE_PAYOUT, STREAK_BONUS, CREDIT_TRANSFER
  Statuses: PENDING, COMPLETED, FAILED, REFUNDED

Layer 3 - CREDIT LEDGER (Audit Trail)
  Model: CreditLedger
  Purpose: Bank-grade double-entry accounting
  Rule: Every credit mutation MUST create a ledger entry
  Constraint: @@unique([type, referenceId]) prevents duplicate processing
  Types: PAYPAL_PURCHASE, STRIPE_PURCHASE, TRANSFER_IN, TRANSFER_OUT,
         SPEND, WITHDRAW, ADJUSTMENT, REVERSAL, ADMIN_GRANT,
         DONATION_IN, DONATION_OUT, SERVICE_PAYMENT, SERVICE_EARNING,
         SERVICE_REFUND, MESSAGE_COST, PLATFORM_FEE_PENDING,
         PLATFORM_FEE_SETTLED, AD_PURCHASE, AD_REFUND,
         AD_IMPRESSION_EARNING, AD_CREATOR_PAYOUT, GAME_GIFT_OUT,
         GAME_GIFT_IN, GAME_HOST_CUT, GAME_PAYOUT

HOW CREDITS FLOW:

  Credits Enter the System:
    - PayPal purchase (real money -> credits)
    - Admin grant (manual adjustment)
    - Streak bonus (automatic reward)

  Credits Move Between Users:
    - Donations in live streams (viewer -> host, with platform cut)
    - Game gifts (viewer -> player, with host cut)
    - Credit transfers (user -> user, no fee)
    - Service payments (buyer -> seller)
    - Message streak bonuses (system -> both users)

  Credits Leave the System:
    - Withdrawals (credits -> PayPal payout)
    - Ad purchases (credits -> ad impressions)
    - FiveM website subscriptions (credits -> service)
    - Power-up purchases (credits -> game effects)

  Platform Revenue Streams:
    - Purchase fees (5% on custom amounts)
    - Withdrawal fees (2%, min $0.25)
    - Donation platform cut (20% default, configurable)
    - Ad impression fees
    - FiveM website fees

6. CREDIT LEDGER (Double-Entry Accounting)
================================================================================

File: src/lib/credit-ledger.ts

The ledger is the backbone of all financial operations. Every credit mutation
follows this pattern:

  1. Check idempotency (has this referenceId+type been processed?)
  2. Open prisma.$transaction()
  3. Create CreditLedger entry with signed delta
  4. Update Wallet.credits atomically
  5. Commit or rollback

KEY FUNCTIONS:

  insertLedgerEntry(tx, entry):
    - For CREDITS (positive delta):
      UPDATE Wallet SET credits = credits + ? WHERE userId = ?
    - For DEBITS (negative delta):
      UPDATE Wallet SET credits = credits - ? WHERE userId = ? AND credits >= ?
      (Race-safe conditional prevents overdraft)
    - Throws error if insufficient balance

  insertLedgerEntries(tx, entries):
    - Batch insert for paired entries (e.g., TRANSFER_OUT + TRANSFER_IN)
    - Processes sequentially within single transaction

  ledgerEntryExists(referenceId, type):
    - Fast idempotency check before starting transaction
    - Returns boolean

IDEMPOTENCY STRATEGY:
  - @@unique([type, referenceId]) at database level
  - External IDs used as referenceId (e.g., PayPal orderID)
  - If entry exists, return success without reprocessing
  - Prevents double-mint from network retries

7. PAYPAL PURCHASE FLOW
================================================================================

Step 1: CREATE ORDER (POST /api/paypal/create-order)
  - Rate limit: 10 orders per user per 10 minutes
  - Minimum: $0.50, Maximum: $500.00
  - Preset packages:
      100 credits  = $0.99
      500 credits  = $4.99
      1000 credits = $9.99
      5000 credits = $39.99
  - Custom amounts also supported
  - Creates PayPal order via REST API
  - Returns orderID for frontend PayPal button

Step 2: CAPTURE ORDER (POST /api/paypal/capture-order)
  - Rate limit: 5 captures per user per 10 minutes
  - Idempotency check: If ledger entry exists for orderID, return success
  - Captures payment via PayPal API
  - Fee calculation for custom amounts:
      PayPal processing: 3.49% + $0.49
      Platform fee: 5% (configurable via PlatformSettings)
      Net credits = floor(amount - total fees)
  - Preset packages: No visible fee (baked into price)
  - Maximum: 50,000 credits per transaction

  Atomic transaction:
    1. Create Transaction record (CREDIT_PURCHASE, COMPLETED)
    2. Insert CreditLedger entry (PAYPAL_PURCHASE, referenceId = orderID)
    3. Update Wallet.credits
    4. Update Wallet.totalSpent
    5. Audit log entry

PayPal Integration Files:
  - src/lib/paypal.ts (getAccessToken, createOrder, captureOrder)
  - Environment: PAYPAL_CLIENT_ID, PAYPAL_CLIENT_SECRET, PAYPAL_MODE


================================================================================
8. WITHDRAWAL FLOW
================================================================================

Endpoint: POST /api/wallet/withdraw

Requirements:
  - Minimum: 500 credits ($5.00)
  - Must have sufficient wallet balance
  - Owner accounts skip all fees

Fee Calculation:
  Fee = max(ceil(grossCredits * withdrawalFeePct / 100), withdrawalFeeMinCents)
  Default: 2% with $0.25 minimum
  Example: 1000 credits ($10) -> 2% fee = $0.20 -> net = $9.80

Atomic Transaction:
  1. Create Transaction (WITHDRAWAL, PENDING)
  2. Insert CreditLedger (WITHDRAW, referenceId = transactionId)
  3. If non-owner: Credit treasury with fee amount
     - Insert CreditLedger (PLATFORM_FEE_PENDING)
     - Update treasury user's totalEarned
  4. Deduct from Wallet.credits

Result: User receives PayPal payout to their email (1-3 business days)

Fee Config (GET /api/wallet/fees):
  Returns: withdrawalFeePct, withdrawalFeeMinCents, purchaseFeePct
  Source: PlatformSettings singleton


================================================================================
9. CREDIT TRANSFERS
================================================================================

Endpoint: POST /api/wallet/transfer

Validation:
  - Amount must be positive integer
  - Sender must have sufficient balance
  - Cannot transfer to self
  - Receiver must exist

Process:
  1. Ensure receiver wallet exists (upsert)
  2. Create Transaction records for both users
  3. Insert double-entry ledger:
     - TRANSFER_OUT: sender  -amount (referenceId = txId)
     - TRANSFER_IN:  receiver +amount (referenceId = txId)
  4. Atomic balance updates
  No fees charged on transfers.

10. DONATION SYSTEM (Live Streams)
================================================================================

Endpoint: POST /api/live/[id]/chat (with isDonation=true)

Parameters:
  - text: Chat message content
  - isDonation: true
  - creditAmount: 1 to 100,000

Host Cut System:
  - Default: 80% to host, 20% to platform
  - Configurable per stream via LiveStream.hostCutPercent (0-100)
  - hostShare = floor(creditAmount * hostCutPercent / 100)
  - platformShare = creditAmount - hostShare

Validation:
  - Stream must be LIVE
  - Sender must not be blocked by host
  - Sender must have sufficient balance
  - Amount must be 1-100,000 credits

Atomic Transaction:
  1. Ensure host wallet exists
  2. Create Transaction for donor (DONATION, creditAmount)
  3. Create Transaction for host (CREDIT_EARNED, hostShare)
  4. Insert ledger entries:
     - DONATION_OUT: donor   -creditAmount
     - DONATION_IN:  host    +hostShare
     - PLATFORM_FEE: treasury +platformShare (if applicable)
  5. Update donor.totalSpent, host.totalEarned
  6. Create LiveChatMessage with isDonation=true, creditAmount

The donation appears in chat with the sender's name and amount.
The host receives their cut instantly in their wallet.

13. TREASURY & PLATFORM REVENUE
================================================================================

File: src/lib/treasury.ts

The treasury is the platform owner's wallet, identified by isOwner=true.

Revenue Sources:
  1. PayPal purchase fees (5% on custom amounts)
  2. Withdrawal fees (2% min $0.25, non-owner only)
  3. Donation platform cut (20% default)
  4. Game gift platform cut (same as donations)
  5. Ad impression fees
  6. Service marketplace fees
  7. FiveM website subscription fees

getTreasuryUserId(tx?):
  - Finds user where isOwner = true
  - Caches result in module scope
  - Used inside atomic transactions

Fee Distribution Example (Donation):
  Viewer donates 1000 credits ($10)
  Host cut: 80% = 800 credits to host
  Platform: 20% = 200 credits to treasury

Fee Distribution Example (Withdrawal):
  User withdraws 1000 credits ($10)
  Fee: 2% = 20 credits to treasury (min $0.25)
  Payout: 980 credits ($9.80) to PayPal

14. AD REVENUE SYSTEM
================================================================================

CUSTOM AD MARKETPLACE:

Submission:
  - Creators submit video ads (title, video URL, duration)
  - Pay creditsPaid upfront (default 5000 credits submission fee)
  - Status: PENDING_REVIEW -> APPROVED/REJECTED
  - Optional: maxImpressions cap, expiresAt date

Serving (GET /api/ads/custom/serve):
  - Rate limited: 30 req/min per IP
  - Weighted random selection by credits remaining
  - Returns VAST 3.0 XML with 10-second skip offset
  - Per impression: deducts costPerImpression from ad balance

Revenue Share (follower-based):
  Followers    | Creator Share | Platform Share
  -------------|---------------|---------------
  20,000+      | 80%           | 20%
  10,000+      | 50%           | 50%
  Under 10,000 | 10%           | 90%

PER-CREATOR AD SETTINGS (AdSettings model):
  - adsPerVideo: Number of ads per video (default 1)
  - adsPerLiveHour: Ads per live stream hour (default 2)
  - creditsToSkip: Credits viewers pay to skip ads (default 200)
  - revenueSharePct: Creator's revenue share percentage

AD IMPRESSION TRACKING (AdImpressionLog model):
  - Records every ad view with full revenue split
  - Tracks paidOut status for payout scheduling
  - adPayoutDay in PlatformSettings (0 = manual only)

15. SERVICE MARKETPLACE PAYMENTS
================================================================================

Endpoint: POST /api/services (create), /api/services/[id]/order (purchase)

Service Categories:
  COACHING, VIDEO_REVIEW, CUSTOM_CONTENT, SHOUTOUT, COLLABORATION, OTHER

Payment Flow:
  1. Buyer places order (ServiceOrder created, status: PENDING)
  2. Credits held: Buyer's wallet debited
     - Ledger: SERVICE_PAYMENT (buyer -priceCredits)
  3. Seller accepts and delivers
  4. Buyer confirms completion
     - Ledger: SERVICE_EARNING (seller +priceCredits)
  5. On dispute/cancellation:
     - Ledger: SERVICE_REFUND (buyer +priceCredits)

Order Statuses:
  PENDING -> ACCEPTED -> IN_PROGRESS -> DELIVERED -> COMPLETED
  Or: PENDING -> CANCELLED / DISPUTED

19. LIVE STREAMING SYSTEM
================================================================================

ARCHITECTURE:
  Ingest: RTMP via Cloudflare Tunnel
  Playback: HLS (HTTP Live Streaming)
  Signaling: WebRTC for peer-to-peer connections
  Real-time: SSE for game state, REST for actions

STREAM LIFECYCLE:
  1. Creator opens /go-live
  2. Selects mode, configures settings, picks devices
  3. POST /api/live creates stream (status: WAITING)
  4. Stream key generated (rly_live_ + 32-char hex)
  5. Creator starts broadcasting -> status: LIVE
  6. Heartbeat every 2 minutes keeps stream alive
  7. Creator ends stream -> status: ENDED
  8. Stale detection: Auto-end if no heartbeat for 2+ minutes

STREAM MODES:
  STANDARD      - Simple broadcast with chat and donations
  TIMER_WARS    - Timed rounds, lowest score eliminated
  TOWER_WARS    - Real-time strategy, units march toward bases
  ROOMS         - Multi-participant rooms
  TRIVIA        - Multiple choice questions, fastest answer wins
  AUCTION       - Item bidding with anti-snipe timer
  SPIN_WHEEL    - Randomized wheel game
  LAST_STANDING - Elimination until one remains

STREAM SETTINGS:
  - Title, tags, game selection
  - Visibility: public, private, followers only
  - Guest limit: 2-10 participants
  - Round length: 15-300 seconds
  - Slow mode: off/5s/10s/30s/60s
  - Recording toggle
  - Host cut percentage (0-100%)
  - Minimum donation amount
  - Background color/image
  - Camera-off and mute overlay images
  - Banned words list, link blocking
  - Followers-only or subscriber-only chat

VIEWER EXPERIENCE:
  - HLS stream playback with volume controls
  - Real-time viewer count
  - Live elapsed time display
  - Chat panel with messages and donation highlights
  - Gift/donation drawer for sending credits
  - Join queue to request guest participation
  - Follow creator button

CHAT SYSTEM:
  - Stored in LiveChatMessage table
  - Cursor-based pagination for history
  - Host can block senders (blocked users get 403)
  - Welcome messages on viewer join
  - Donation messages highlighted with amount
  - Moderation: slow mode, banned words, followers-only

RECORDING:
  - Optional per-stream
  - States: Recording -> Paused -> Stopped
  - Duration tracked in real-time
  - Chunk-based upload on completion
  - Post-processing for thumbnail generation

20. BATTLE & GAME SYSTEMS
================================================================================

GAME ENGINE ARCHITECTURE:
  File: src/lib/games/game-engine.ts

  GameEngine manages:
    - 100ms tick interval (10 FPS game logic)
    - Action processing (user inputs)
    - State broadcasting via SSE
    - Callbacks: onStateUpdate, onGameEnd, onElimination

  Game State Structure:
    gameId, streamId, mode, phase, round, maxRounds,
    timeRemaining, players, winner, data (mode-specific)

  Phases: waiting -> active -> paused -> finished

  SSE Broadcasting:
    - Full listeners: Complete state every tick
    - Overlay listeners: Diff updates at ~12 FPS
    - 15-second heartbeat keepalive

PARTICIPANT ROLES:
  HOST   - Stream creator, full control (create/start/end game)
  GUEST  - Approved by host, can submit game actions
  VIEWER - Can donate/chat, cannot interact with game

GUEST APPROVAL:
  1. Guest joins with role: "guest"
  2. Created as PENDING participant
  3. Host approves -> transitions to ACTIVE
  4. Only ACTIVE guests can submit game actions

---------- TIMER WARS ----------
File: src/lib/games/timer-wars-server.ts

Mechanics:
  - Timed countdown each round
  - Lowest scorer eliminated at round end
  - Tied at bottom: all tied players eliminated
  - Last remaining player wins
  - Or highest scorer after max rounds

Player State: score, isEliminated, team (optional), rank

Features:
  - Victory lap: 3-minute celebration after winner
  - Top gifters tracked (up to 10)
  - Team mode: aggregate team A vs team B
  - Specific-gift mode: only certain tiers count
  - Rejoin queue for eliminated players

Payout:
  - On elimination: player gets accumulated playerEarnings
  - Automatic payout via database transaction
  - Auto-restart after 5 seconds

---------- TOWER WARS ----------
File: src/lib/games/tower-wars-server.ts

Mechanics:
  - Units spawn and march toward opponent base (position 0->100)
  - Combat in center zone (position 40-60)
  - Units reaching position >= 100 damage target base
  - Base destroyed = player eliminated

Unit System:
  - Each gift tier maps to unit stats (HP, damage, speed)
  - Units tracked with: id, tierId, senderId, supportingId,
    targetId, hp, maxHp, damage, speed, position
  - Healing units restore base HP

Game Modes:
  - V1 Single Tower: One objective, destroyed = instant win
  - V1 Single Lane: All units on same lane
  - Legacy Elimination: Multiple players, bases eliminated

Actions:
  - spawn_unit: Create unit from gift tier
  - heal: Restore base HP (capped at maxBaseHp)

---------- TRIVIA BATTLE ----------
File: src/lib/games/trivia-battle.ts

Mechanics:
  - Host sets questions (typically 5)
  - Players answer; fastest correct answer = highest score
  - Scoring: 100 + (timeRemaining * 10) points
  - First correct: +50 bonus points
  - Wrong answer: 0 points, marked as answered
  - 3-second reveal phase between questions

Actions:
  - set_questions: Host loads question bank
  - answer: Player submits answerIndex
  - donate: Score += floor(amount / 2)

---------- AUCTION WARS ----------
File: src/lib/games/auction-wars.ts

Mechanics:
  - Items presented one at a time with starting bid
  - Real-time bidding with countdown
  - Anti-snipe: Extends timer to 10s if bid in last 5s
  - Highest bidder wins item
  - Winner determined by most items won

Actions:
  - set_items: Initialize auction
  - bid: Submit new bid (must exceed current high)
  - donate: Amount added to score

BATTLE INVITATIONS:
  Endpoint: /api/battle/invite
  - Search live creators to invite
  - 5-minute expiration
  - Optional custom message

LEADERBOARD:
  - Real-time scoring, sorted by score descending
  - Top 3 supporters with Gold/Silver/Bronze styling
  - Top 3 supporters earn free power-ups

SPLIT SCREEN BATTLE:
  - Left player (blue) vs Right player (red)
  - Score display with animations
  - Magic Mist renders score as "???"
  - Compact variant for mobile

21. VIDEO UPLOAD & PROCESSING
================================================================================

UPLOAD FLOW:
  1. User selects file on /upload page
  2. Frontend chunks file into 10MB pieces
  3. POST /api/upload/chunk for each chunk
     - Resume support (checks existing chunks)
     - Auto-retry up to 5 times with exponential backoff
  4. Metadata saved: title, description, tags, visibility, series
  5. Thumbnail selection (auto-generated or custom upload)

PROCESSING PIPELINE (src/lib/video-processing.ts):
  1. FFprobe detects duration/resolution
  2. FFmpeg encodes two variants:
     - Main: 720p, H.264, CRF 23, fast preset
     - Low: 360p, CRF 28 for low bandwidth
  3. Both use -movflags +faststart for instant playback
  4. Fixed 2-second GOPs (48 keyframes at 24fps)
  5. AAC audio at 128k

VIDEO STATUSES:
  PROCESSING -> READY (success) or FAILED (error)
  DELETED (soft delete, never hard-deleted)

VIDEO VISIBILITY:
  PUBLIC         - Anyone can see
  UNLISTED       - Only accessible via direct link
  PRIVATE        - Only creator can see
  FOLLOWERS_ONLY - Only creator's followers can see

ALTERNATIVE UPLOAD ROUTES:
  /api/upload/session         - Initialize upload session
  /api/upload/chunk-json      - Base64-encoded chunk (no FormData)
  /api/upload/stream-gallery  - Camera-off/mute overlay images

VIDEO MANAGEMENT:
  GET /api/videos/[id]    - View video details
  PUT /api/videos/[id]    - Update metadata
  DELETE /api/videos/[id] - Soft delete

  connectivity.ts:
    - Monitors online/offline state

API LAYER (src/lib/api.ts):

  - Mutations queued when offline (POST/PUT/DELETE)
  - Graceful fallback to cached data on network errors
  - Admin endpoints excluded from offline support

SYNC FLOW:
  POST /api/sync/actions   - Batch process queued offline actions
  GET /api/offline/version - Check client/server compatibility

WHAT WORKS OFFLINE:

29. SECURITY & ANTI-FRAUD
================================================================================

RATE LIMITING (src/lib/rate-limit.ts):
  - In-memory sliding window counter
  - Per-key tracking (IP, email, user)
  - 5-minute cleanup interval
  - Examples:
    - PayPal create-order: 10/user/10min
    - PayPal capture: 5/user/10min
    - Auth login: 25/IP/10min, 10/email/10min
    - Auth register: 10/IP/hour, 5/email/hour
    - Ad serve: 30/IP/minute

FINANCIAL SECURITY:
  - Ledger idempotency: @@unique([type, referenceId])
  - Race-safe debits: Conditional SQL prevents overdraft
  - Atomic transactions: prisma.$transaction() for all mutations
  - PayPal order verification before credit mint

AUTHENTICATION SECURITY:
  - JWT in httpOnly, secure, sameSite=lax cookies
  - Password hashing: bcryptjs with 12-round salt
  - Device gating for owner accounts
  - Session expiry (30 days)
  - Age gate enforcement (13+)

CONTENT SECURITY:
  - Block system prevents interaction with blocked users
  - Stream host can block chat senders
  - Moderation tools: banned words, slow mode
  - Report system for users/videos/comments

SECURITY POLICY (src/lib/security-policy.ts):
  - Account restriction checks (isBanned, isDeactivated)
  - Owner device gate enforcement
  - IP extraction from forwarded headers

INPUT VALIDATION:
  - Amount ranges on all financial endpoints
  - User existence verified before transfers
  - File type/size validation on uploads
  - Enum enforcement on all status fields

AUDIT LOGGING:
  - PayPal captures logged with full details
  - Failed login attempts tracked
  - User registration metadata stored
  - Admin actions recorded

ENCRYPTED STORAGE:
  - Streamlabs tokens encrypted in database
  - OBS WebSocket passwords encrypted
  - Stream keys stored securely
  - Returned masked to frontend
